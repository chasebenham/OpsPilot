# AI request intelligence

The frontend explicitly posts a draft to the versioned backend API. The OpenAI Python SDK sends separate system and untrusted user messages to the Responses API with Pydantic Structured Outputs and `store=False`. The validated result, input-description hash, model identifier, usage and owner are stored in `ai_analyses`; no raw provider dump, key, reasoning or duplicate input description is retained. Extracted values can themselves be sensitive. Drafts have no automatic expiration in this prototype. API access uses the existing demo identity and role model, which is impersonable and not production authentication.

`AnalysisResult` in `backend/app/ai_schemas.py` defines supported types, priority and department enums, summary, impact, explanation, missing questions, review flag and nullable IT, purchase and project extraction fields. Null represents unavailable facts. The model is instructed to extract explicit facts, ignore instructions inside the draft, flag ambiguity and refrain from taking actions. Schema validity is not proof of factual correctness or prompt-injection resistance.

Analysis never changes a request. On submission the server locks the owned unlinked analysis, checks the description hash, stores the original result, selected recommendations and final request values, and records a review event in the same transaction as request creation. A management-authorized user can attach their own current analysis to an existing request via `/ai-review`; analysis history follows request visibility. Critical incident submissions, critical recommendations and suspected security concerns trigger deterministic review flags. Department recommendations are advisory and never assign work. The application cannot guarantee every security issue is detected; humans must review all output.

With no key, timeout, provider failure, refusal, incomplete or invalid output, an actionable error is returned; no fabricated result is substituted. Input and output limits and timeout are configurable. Calls have no automatic retries; each click is an explicit potentially billable request. Only token counts and model name are logged, not request content. Manual submission remains available.

## Cost and evaluation

The default `gpt-6-luna` supports Structured Outputs. The published standard text rates at documentation time were $0.10 per million input tokens and $0.50 per million output tokens; cached input, cache writes, regional processing and other modes may differ. These are assumptions, not measured spend; consult [model pricing](https://developers.openai.com/api/docs/models/gpt-6-luna) and account billing. Model access and prices can change.

`backend/evaluation/cases.json` contains 30 fictional labeled requests. `python -m evaluation.run --live --limit 30` sends the selected synthetic cases to the provider and incurs charges; it reports classification and priority agreement, routing agreement, review recall for labeled cases, simple substring extraction and missing-question keyword checks, invalid/error rates and reported usage. Accuracy metrics for classification, extraction and missing details use successful responses as denominators, while review recall counts provider failures as misses. These labels are illustrative and subjective, and substring checks are imperfect. Spend is not returned by the API; inspect billing. No mocked test is a measure of live model performance. The `--live` flag and a key are required.

See [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) for schema and refusal limitations.
