# Analytics methodology and disclosure limitations

Analytics are restricted to simulated department managers and Operations Admins. Managers see requests currently assigned to their department; Operations Admins can view organization-wide aggregates. Task-only access does not grant project visibility. Demo-user selection is not authentication; anyone who can select another demo identity can impersonate it.

The Analytics workspace queries only a separately provisioned local PostgreSQL database with the `meridian-synthetic-v1` marker. Its initialization refuses existing unmarked records and the endpoint uses read-only transactions. Exact counts and filters apply only to that isolated fictional dataset. The ordinary database is not read for synthetic metrics. The existing general analytics endpoint continues to reject filters and return coarse count bands. Neither simulated identity nor this local isolation is production security; an operator must not place genuine records in the synthetic database.

The underlying service selects a request-creation cohort with America/Phoenix dates converted to UTC; state metrics represent current states, not historical backlog snapshots. Open means Submitted, Needs Information, Triaged or In Progress; Resolved and Closed are separate. Resolution time uses the earliest recorded transition to Resolved. Missing and invalid timestamps are excluded. The underlying approval duration uses only latest cycles where every stage is approved, from earliest stage creation to last decision. Authorization is not payment. The latest SLA revision is used; on-time acknowledgment divided by acknowledged incidents is not a rate for unacknowledged incidents. Escalated incident counts use distinct request IDs; escalation records count separate reasons. Task duration includes completed tasks with both timestamps, and handoffs count recorded unblocked events. Routing completion is not routing correctness.

Charts show requests by creation month, acknowledgment events by month on the latest SLA revision, approval-stage decisions by decision month, and completed projects by completion month. The selected dates filter the parent request creation cohort rather than event timestamps. Times are America/Phoenix; seeded records represent fictional examples rather than observations from an actual company. Historical backlog is not reconstructed. Stage waiting is measured from a recorded stage-ready event to the decision (including historical cycles); readiness to start uses the first recorded task-ready or unblocked event and a start timestamp; handoff time uses the final prerequisite completion to the successor's first ready event, only when every prerequisite has a completion timestamp. Negative durations and records without the necessary events are excluded. Task-ready, task-unblocked, task-in-progress and approval-decision events are captured prospectively; approval-stage-ready events now record when each sequential stage is first actionable. Older histories can be incomplete, and synthetic records created before the instrumentation will often have insufficient data. No missing duration is fabricated.
