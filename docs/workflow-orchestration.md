# Cross-department workflow orchestration

Meridian's fictional project requests need coordinated departmental ownership and auditable handoffs. A request can have one project workflow. Workflow plans are versioned drafts; only an explicitly approved plan creates executable tasks and dependency edges. Request, workflow, plan, task, edge and event records are persisted in PostgreSQL. The parent request row is locked before workflow mutations so concurrent task completion cannot produce duplicate handoffs.

## Lifecycle and permissions

Create a workflow from an eligible Cross-Department Project request. Its requester is the project owner. The owner, an Operations Admin, or the manager of the request's assigned department can edit and submit plans and approve activation. Save edits before submitting or activating. Drafts cannot execute. At activation the plan is validated and materialized atomically; the parent moves to In Progress. The project owner or admin explicitly completes the project only when all required tasks are Completed; the request becomes Resolved. Cancellation is audited and cancels unfinished tasks. Completed and cancelled workflows and tasks cannot be reopened; create a new request for a revised execution plan. Approved active plans cannot be edited in this phase.

Tasks with no prerequisites start Ready; others remain Blocked until every predecessor is Completed. Cancelled predecessors do not satisfy dependencies. Completing a task updates eligible successors to Ready in the same transaction and records system handoffs. Cycles, duplicate keys or edges, self-dependencies, and references outside the plan are rejected. A workflow with required unfinished tasks and no Ready or In Progress task is Blocked. Optional tasks do not need to be completed for final authorization, but cannot satisfy dependencies while cancelled.

The owner or manager may assign departments; department managers may assign eligible active users in their own department. Assigned users, their department manager and Operations Admin may perform allowed task actions. The request's original visibility rules remain in force: assignment to a task does not grant access to its parent request, AI history or the full project. The Workflows page provides a scoped My Tasks section with only permitted task information and a count of unmet prerequisites. Full project details remain restricted to users who can already view the parent request. The demo switcher is not authentication and is not safe for production exposure.

## AI assistance

An optional explicit OpenAI Responses call generates a structured draft. The provider receives the project title and description, and no employee is automatically assigned. Department names, priorities, task keys and dependency graphs are validated before a draft is saved. The model cannot activate a project, assign employees or bypass permissions. A changed source description marks an unapproved AI plan stale; regenerate it or explicitly save a manual plan, then submit and approve. AI output can be wrong or manipulated; a person must review it. Missing credentials, refusals and provider errors leave manual planning available. The service captures the authorized request and plan version, releases its database session while the provider responds, then locks and rechecks the actor, request, workflow, plan and department references before saving. A changed or concurrently activated project rejects the stale suggestion instead of overwriting work.

## Demonstration and testing

`python -m app.seed` adds separately named, fictional marketing launch, onboarding, process improvement and draft examples without modifying existing requests. The marketing example includes a completed brief, parallel ready work, blocked QA and launch, and an overdue design task. Open Workflows as the marketing requester or an Operations Admin and select the campaign. Open task details, switch to an assigned demo user to start and complete work in My Tasks, then observe the owner/admin project view update. Complete all required tasks before the owner authorizes completion.

Run backend tests with `python -m pytest -q`; set `TEST_POSTGRES_URL` and run `python -m pytest -q tests/test_postgres_integration.py` for isolated PostgreSQL checks. Frontend tests and build run with `npm.cmd test` and `npm.cmd run build`. A single synthetic, billable AI planning check is opt-in: `python -m app.project_live_eval --live`. It validates the schema, actual departments and acyclic graph, reports token usage and, for the documented default model, an estimated uncached standard cost; actual billing may differ.

This prototype has no real authentication, external notifications, scheduling optimizer, automatic employee assignment or active-plan revision workflow. It uses browser-local time when entering and displaying dates and stores timezone-aware timestamps. A department manager can change assignments within their department; cross-department transfers require the project owner or the request's manager/admin. All demo records and organizations are fictional.
